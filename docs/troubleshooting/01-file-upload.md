# 01. 운영 환경 파일 업로드 실패 — 4개 레이어 추적

| 항목 | 내용 |
| --- | --- |
| 발생 | 2026-05-26 ~ 27 |
| 영향 | 이력서 업로드 → AI 분석 기능 전체 불가 (서비스 핵심 기능) |
| 범위 | CloudFront · AWS WAF · 프론트 요청 코드 · Spring multipart 설정 |

## 접근 방식

에러 코드가 바뀔 때마다 "요청이 어느 레이어까지 도달했는가"를 기준으로 범위를 좁혔다.

```
Browser ─▶ CloudFront ─▶ WAF ─▶ EC2(Nginx) ─▶ Spring Boot ─▶ S3 / AI 서버
            ① 라우팅     ② 차단               ③ 경로 · ④ 형식/용량
```

| 관찰한 응답 | 판단 | 다음 확인 위치 |
| --- | --- | --- |
| 200 + `index.html`, `server: AmazonS3` | API 요청이 S3 Origin으로 감 | CloudFront Behavior |
| 403, `Generated by cloudfront` | Origin 도달 전 엣지에서 차단 | WAF Sampled requests |
| 500, `COM-500-001` | 앱까지 도달, 내부 처리 실패 | `journalctl -u nextplan` |

---

## ① CloudFront: API 요청에 `index.html` 반환

**증상**
```
POST /api/fileupload  → 200 OK
server: AmazonS3
content-type: text/html
<!doctype html> ... (React index.html)
```

**원인**
- Distribution에 Default Behavior(`*` → S3) 하나만 존재 → `/api/*` 요청도 S3로 전달
- SPA 라우팅용 에러 응답 설정(403/404 → `/index.html`, 200) 때문에 실패가 성공처럼 보였음

**조치**
- Behavior 추가: Path pattern `/api/*` → Origin: EC2
- Allowed methods: `GET, HEAD, OPTIONS, PUT, POST, PATCH, DELETE`
- 캐싱 비활성화 (API 응답은 사용자별)

**포인트**: 응답 헤더 `server` 값 하나로 요청이 도달한 Origin을 즉시 판별

## ② AWS WAF: `403 Request blocked`

**증상 (CloudFront 생성 에러 페이지)**
```html
<H1>403 ERROR</H1>
<H2>The request could not be satisfied.</H2>
Request blocked.
Generated by cloudfront (CloudFront)
```

**분석: WAF & Shield → Web ACL(Global) → Sampled requests**
```
POST /api/fileupload HTTP/2.0
host: <cloudfront-domain>
content-type: multipart/form-data; boundary=----WebKitFormBoundary...
authorization: Bearer <masked>
content-length: 646887

Action: BLOCK
Terminating rule: AWS#AWSManagedRulesCommonRuleSet#SizeRestrictions_BODY
```
→ 약 631KB 요청 본문이 Core Rule Set의 본문 크기 제한(8KB)에 걸림

**선택지 검토**

| 방법 | 결과 |
| --- | --- |
| Web ACL을 CloudFront에서 분리 | 불가 — `You are not able to add or remove resources from a CloudFront Distribution with a CloudFront flat-rate pricing Free plan.` |
| Body 검사 한도 상향 | 기본 16KB 초과분은 추가 과금, 수 MB 파일에는 근본 해결 아님 |
| **`SizeRestrictions_BODY`만 Block → Count** | ✅ 채택 — 비용 0, SQLi/XSS 등 나머지 규칙 유지 |
| Presigned URL로 S3 직접 업로드 | 근본 해결. 구조 변경 필요 → 개선 과제 |

**결과**: 403 해소 → 500으로 증상 변화 (= 요청이 앱까지 도달)

## ③ 경로 중복: `500 COM-500-001`

**응답**
```json
{"code":"COM-500-001","message":"서버 내부 오류"}
```

**서버 로그**
```
$ sudo journalctl -u nextplan -n 100 --no-pager
... NoResourceFoundException: No static resource api/api/fileupload
```

**소거법으로 추적**
1. 백엔드 컨트롤러 `@RequestMapping("/api/fileupload")` → 정상
2. 프론트 `baseURL = VITE_API_BASE_URL` = `https://<cloudfront-domain>` → 정상 (`/api` 미포함)
3. 업로드 컴포넌트에서 발견
   ```ts
   const endpoint = import.meta.env.PROD ? /api/api/fileupload : /api/fileupload;
   ```

**원인**: ①번 라우팅 문제가 있던 시기에 운영에서만 경로를 바꿔 끼운 임시 우회 코드가 남아 있었음
**조치**: 환경 분기 제거, 단일 경로 `/api/fileupload`

**포인트**: 인프라 문제를 코드에서 우회하면, 인프라를 고친 뒤 그 우회가 새 장애가 된다

## ④ multipart 형식 · 용량

| 원인 | 조치 |
| --- | --- |
| Axios 인스턴스 기본 헤더 `Content-Type: application/json` 고정 → `FormData` 전송 시 boundary 누락 | 기본 헤더 제거, 브라우저가 `multipart/form-data; boundary=...` 자동 설정 |
| Spring Boot multipart 기본 한도 1MB | `max-file-size`, `max-request-size` 50MB |

## 결과 & 후속

- 업로드 → S3 저장 → AI 분석 요청까지 운영 환경 정상화
- 후속 개선: AI 분석을 비동기 처리로 분리(업로드 응답은 분석 ID만 즉시 반환), 외부 호출 타임아웃 3분 지정
- 남은 과제: 업로드를 Presigned PUT URL 방식으로 바꿔 WAF 예외 규칙 자체를 없애기
